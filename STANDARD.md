# Skill standard

This is the specification every Timerise skill follows and the practice behind it. A new skill is listed in
the index when it meets this standard; an existing skill that drifts from it is brought back before its next
release. It is written for the engineer building a skill, and for an agent asked to build or review one.

## 1. What a skill is

A skill teaches an agent to build **one production-grade module** for a **Next.js App Router** app, on the
host app's own stack, the way our engineers build it after shipping it many times. It is one repository
under `github.com/timerise-ai`, in the open [Agent Skills](https://agentskills.io) format, so the same folder
works in Claude Code, Codex CLI, Gemini CLI and any other skills-compatible agent.

- **One module per skill.** A blog, a help center, a kiosk, a signage system, a settlement flow, an
  e-invoicing integration, a fallback server. Not a framework, not a starter kit, not a grab bag.
- **Markdown only, plus optional runnable assets.** No build, no `package.json`, no file that calls a model.
  Code inside a skill describes the app the agent will generate, never this repository.
- **Portable across backends.** The data layer sits behind an explicit seam. The host app's auth, tenancy,
  styling and i18n stay the host app's.
- **Agent-agnostic.** Nothing in a skill is specific to one agent. Installation is a clone or one
  `npx skills add` command.

## 2. Origin and honesty

A skill is written by the engineer who owns the module it describes, from what they have learned building
and rebuilding that module over the years. It is the engineer's know-how written down: the way they build the
module now, after every version of it they have shipped. It is not synthetic: no skill is generated by a
model from a prompt. Where a skill wraps someone else's API, it starts from that vendor's own specification,
corrected against what integrating it taught us.

The skill describes the module the agent will generate. It is not a copy of any one system, and every file
in the repository has to read that way, to a person and to a tool summarising it.

- **Say who wrote it and from what.** The README intro says the module is written by the engineer who has
  shipped it, and names the kind of module it is: a marketing-site blog, a venue kiosk, a marketplace
  settlement flow. Where the skill reports an audit or a measurement, call the thing it was checked against
  **the earlier implementation**, in the singular, without saying whose it was.
- **Say what the templates guarantee, not what broke.** The README intro, the `SKILL.md` framing paragraph,
  the frontmatter description and `CLAUDE.md` describe the module by the properties it holds: every article
  reachable from the sidebar, from search and from an untranslated locale; one file read per post per build;
  a booking priced on the server. They do not count defects, tell what went wrong in the earlier
  implementation, call anything silent or broken, or say the templates exist so that something "cannot
  recur". Each property is stated as what the build and the tests verify. The record of what the audit
  changed lives in `provenance.md`, linked from the front door and not summarised there. The same applies to
  the hard rules and the non-negotiables: the rule, then the reason it holds, without the anecdote.
- **Never identify a system.** No customer, project, brand, domain, industry detail or combination of
  figures that would let a reader work out which deployment the earlier implementation was. A scale figure
  is allowed when it explains a design decision and identifies nothing: "three locales" does, a post count
  next to an industry and a city does not.
- **Banned words.** "Extracted", "extraction", "ported from", "lifted from", "taken from". "The source",
  "the source app", "the source module", "the source repo", "the original module". "Production-tested",
  "production-audited", "battle-tested", "running in production at". Say what the skill carries instead:
  "verified by the build and the tests", "measured on the earlier implementation", "the rule that
  survived three rebuilds". This applies to the `description` in the `SKILL.md` frontmatter as much as to
  the prose: the description is the sentence most often quoted back.
- **Do not deny.** State what the skill is. Never write sentences of the form "not taken from a customer",
  "no customer code": a denial reads as defensive and raises the question it answers.
- **Separate three things in `provenance.md`:** what the audit changed and how the templates verify it,
  what was kept deliberately with the reason it is safe, and what was designed in the skill and has never
  run in production. The skill's credibility is that it distinguishes them. `provenance.md` is an engineering
  ledger for the person editing the skill, not a story for the reader of the README.
- **No corpus figures.** How many articles, posts, files, tags, locales, screens or sellers the earlier
  implementation had, and ratios such as "25 of 45 links", do not appear anywhere: they describe one
  deployment, together they fingerprint it, and none of them changes how the next implementation is built.
  Say the shape instead: "half a category", "most translated posts", "a two-word tag with and without a
  hyphen". Numbers that stay are the ones the next implementation needs: design parameters (a 200-item
  cap, a 15-minute TTL, a 32 px touch target), vendor and API facts, the skill's own test and fixture
  counts, and the ledger's own entry count inside `provenance.md`. A single measured magnitude that argues for a rule, such
  as a 71x read amplification, may stay as that one figure without the corpus behind it. Do not restate a
  number loosely and do not invent new ones.
- **Every claim is verifiable.** If a fact about a library, an API or a status code changes, say how it was
  verified: against the library, the docs, or a reproduction. Never from memory.

## 3. Repository layout

| Path | Required | Contents |
|---|---|---|
| `SKILL.md` | yes | Entry point: frontmatter trigger, architecture, critical facts, hard rules, quick start, reference directory |
| `README.md` | yes | Human-facing front door, in the fixed section order of section 6 |
| `CHANGELOG.md` | yes | Keep a Changelog, one section per release, newest first |
| `CLAUDE.md` | yes | What the repository is and its editing conventions, for an agent editing the skill itself |
| `LICENSE` | yes | MIT |
| `references/*.md` | yes | One concern per file, loaded on demand |
| `references/adaptation.md` | yes, or stated substitute | The seam contract with the host app and the non-negotiables. A skill may keep the seam in `SKILL.md` or its architecture reference instead; `SKILL.md` then says so |
| `references/provenance.md` | yes, or stated substitute | The audit record of section 2. An integration skill written from a vendor specification may keep this record in `CHANGELOG.md`; `README.md` then says so |
| `assets/` | optional | Runnable files a reference points at rather than inlines: example scripts, a test suite carried into the target project |

The repository name, the `name` in the `SKILL.md` frontmatter, the README title and the slash command are the
same kebab-case string.

## 4. `SKILL.md`

The agent loads `SKILL.md` whole on every activation, so it stays short: 130 to 160 lines. Everything
longer goes to `references/`.

**Frontmatter.** Two fields.

- `name`: the repository name.
- `description`: the trigger surface, as one folded paragraph. In this order: what the skill builds, in one
  sentence; `Use when:` followed by numbered situations; `the user mentions:` followed by the vocabulary a
  request would contain, including file names, library names and error codes; what the skill carries that a
  generic answer would not; the framework it targets and the seam that makes it portable; what it is not.

**Body.** These headings, in this order.

1. Title and a short framing paragraph stating the one idea the design turns on.
2. `## When to use` and `## When NOT to use`.
3. `## Architecture`: a diagram in a fenced block and the components it shows.
4. `## Critical facts`: the numbered facts an implementer must hold, each one sentence in bold followed by
   the reason.
5. `## Hard rules`: the non-negotiables. The same list, in the same order, as the README's non-negotiables
   section.
6. `## Quick start`: the ordered steps to build the module, each naming the reference to read.
7. `## Reference directory`: a table mapping the words in a task to the file that answers it.

## 5. `references/`

- **One concern per file.** Data model, backend specifics, routes, UI, operations, extensions, testing. A
  reference is read only when a task needs it, so it must stand on its own and name what it assumes.
- **Code blocks name their destination on the first line** as a comment, for example
  `// lib/blog/posts.ts`. A continuation block that extends a file already introduced omits it.
- **Templates compile.** Every TypeScript block is written to pass under `strict` and
  `noUncheckedIndexedAccess`, with imports complete and types explicit. Where the repository checks this,
  `README.md` says how.
- **Identifiers are shared across files.** A function, type, constant or frontmatter field named in one
  reference has the same name in every other. Rename in all of them or none.
- **Links are relative.** `[x.md](references/x.md)` from `SKILL.md`, `[x.md](x.md)` between references.
- **`adaptation.md`** carries the seam contract: what the host app must already provide, the domain rename
  table from the skill's canonical vocabulary to the host's, the storage, auth, tenancy, styling and i18n
  integration points, the order of work, and the non-negotiables restated.
- **`provenance.md`** carries the audit ledger of section 2 and must stay truthful. Anything that changes a
  template adds an entry: a new defect fixed, a questionable earlier choice kept with the reason, or
  something added that the earlier implementation never ran.
- **The odd-looking parts stay.** An empty options object, a fallback parser, a filter that seems redundant:
  each encodes a documented defect. Check `provenance.md` before simplifying anything.

## 6. `README.md`

The README is the same shape in every skill, so a reader who has seen one knows where to look in the next.
Sections in this order; optional ones are marked.

1. **Title**: `# <name>`.
2. **Badges**, one line each: Agent Skills open format, skills.sh `npx skills add`, Claude Code compatible,
   Codex CLI compatible, Gemini CLI compatible. Copy them from an existing skill.
3. **Intro**: one paragraph stating what the skill teaches an agent to build and for which framework; one
   paragraph with the insight the whole design turns on, in bold; one paragraph on origin in the words of
   section 2: who wrote it, the kind of module the earlier implementation was, and the properties the
   templates verify, linking `references/provenance.md` for the record.
4. `## Install`: the one-command install first, `npx skills add timerise-ai/<name>`, with the `-a` form for
   named agents. Then `### Manual install`: the clone for Claude Code, the project-scoped clone, the symlink
   for other agents, `git pull` to update, and the line `The current release is **X.Y.Z**. See
   [CHANGELOG.md](CHANGELOG.md).` That line is the version the release process updates.
5. `## Activation`: the tasks and phrases that activate the skill automatically, and the explicit
   invocation in each host: `/<name>` in Claude Code, `$<name>` in Codex CLI, `/skills` in Gemini CLI. Say
   that each host matches its own way and that a first run should invoke explicitly.
6. `## What's inside`: the file table, one row per file in the repository, then a paragraph on where the
   seam lives and what it bounds.
7. `## The N non-negotiables`: a numbered list, each item a bold rule followed by the reason it holds and
   what verifies it. The same list as `SKILL.md`. Close with the sentence that everything else is the host app's.
8. Optional, as the module needs: `## Adaptation`, `## Requirements`, `## Security`, `## Verification`,
   `## Links`.
9. `## Not this`: a two-column table of neighbouring problems and where to go instead, naming the sibling
   skill when one exists.
10. `## Contributing`: two paragraphs in a fixed shape, with three slots filled per skill. The first opens
    with "Issues and pull requests are welcome here", states what the repository is and what is checked, and
    says that a changed factual claim must say how it was verified, naming the sources for this skill. The
    second says that adding, removing or renaming a reference means updating the quick start, the reference
    directory and the file table; names the ledger, `provenance.md` or the changelog, that must stay truthful
    and gain an entry for any change; and closes with Conventional Commits, a link to this file for releases,
    and `CLAUDE.md` for the full conventions.
11. `## Part of the Timerise Skills`: the fixed footer, copied from an existing skill. It links the index,
    says the modules are written by our own senior engineers from the modules they have shipped and are not
    synthetic, and describes the shared layout.
12. `## Author`: `Built and maintained by [Timerise](https://timerise.ai).`
13. `## License`: `MIT. See [LICENSE](LICENSE).`

## 7. Writing style

- **Plain punctuation.** No em-dashes, en-dashes, arrows, middle dots or smart quotes anywhere in prose,
  tables or headings. Use a comma, a colon, a full stop or a conjunction. Write a range as "1 to 4", not with
  a dash. Write a flow as a sentence, not as a chain of arrows. The only non-ASCII characters are those in
  proper names.
- **Wrap prose at 110 columns.** Table rows and commands stay on one line.
- **Lead with the fact.** The first sentence of a section states what is true; the reason follows. Bold the
  rule, not the explanation.
- **Name things once.** Canonical vocabulary is defined in one place and reused. The host's rename of that
  vocabulary is a table in `adaptation.md`, not an aside repeated in each reference.
- **Be specific about hosts.** Claude Code, Codex CLI and Gemini CLI are named where invocation or paths
  differ. Nothing else in the text assumes one agent.
- **No attribution to tools.** No generated-by lines, no assistant trailers, no session links, in files or
  in commit messages.

## 8. `CLAUDE.md`

Written for an agent editing the skill repository itself. Three sections.

- **What this repository is**: a skill package, markdown only, nothing executes here; the commands and code
  in `references/` describe the generated app, not this repository; where the skill came from and that
  `provenance.md` is the rationale layer.
- **Structure**: what each file carries, in a few bullets.
- **Editing conventions**: code blocks name their destination; identifiers are shared across files; keep the
  reference directory in `SKILL.md`, the quick start in `SKILL.md` and the file table in `README.md` in sync;
  the odd-looking parts stay; measured numbers are load-bearing; additions are marked as additions; the
  non-negotiables are never presented as optional; which names the host renames and which are the authoring
  contract.

## 9. Versioning and releases

Every skill is versioned on its own line. There is no shared version across skills, and the index is
versioned separately. All of them follow one release standard.

- **Semantic Versioning.** A change to `README.md`, `CLAUDE.md` or wording alone is a PATCH. A new
  reference, a new extension, a new backend or a new asset is a MINOR. A change that breaks the seam
  contract, renames canonical vocabulary the host relies on, or changes a non-negotiable is a MAJOR, and
  the changelog says what broke and how to migrate.
- **`CHANGELOG.md`** follows Keep a Changelog. Each release is `## [X.Y.Z] - YYYY-MM-DD`, newest first,
  opened by one or two sentences saying what the release is, then `### Added`, `### Changed`, `### Fixed`
  and `### Removed` as needed. A documentation-only release says so in its first line and names the version
  the skill content is unchanged from.
- **The version lives in three places** and they agree: the newest changelog section, the current-release
  line in `README.md`, and the git tag.
- **The release commit** is `chore(release): X.Y.Z` and contains only `CHANGELOG.md` and the README
  version line. Nothing else rides in it.
- **The tag** is `vX.Y.Z` on that commit.
- **The GitHub Release** is titled `vX.Y.Z`, created from that tag, with the changelog section for that
  version as its notes and nothing else. Every tag has a Release; a tag without one is a gap to fill.
- **Push** `main` and the tags together. A release is published when the tag and the Release are on GitHub.
- **Commits** between releases follow Conventional Commits: `docs(readme): ...`, `feat(references): ...`,
  `fix(templates): ...`. The release process reads them to decide the bump. No attribution trailers.

## 10. Publishing a new skill

1. Create `timerise-ai/<name>`, public, default branch `main`, MIT license.
2. Build the repository to sections 3 to 8. Run the defect audit on the earlier implementation before
   writing templates, and write `provenance.md` as you go rather than afterwards.
3. Review against the checklist in section 11.
4. Release `0.1.0` under section 9: changelog section, README version line, `chore(release): 0.1.0`,
   tag `v0.1.0`, push, GitHub Release.
5. Add the skill to the index, in this repository, in every place that lists skills: the skills table with
   version, one-line summary and backend; the clone loop under *Manual install*; the activation examples;
   the slash-command list; and the layout table, if the skill keeps its seam or its provenance record
   somewhere other than the default files.
6. Release the index: adding a skill is a MINOR; updating a version in the table is a PATCH.

## 11. Checklist

Before a release, every line holds.

- `SKILL.md` is 130 to 160 lines, its frontmatter has `name` and a `description` in the order of section
  4, and its hard rules match the README's non-negotiables.
- The reference directory in `SKILL.md`, the quick start in `SKILL.md` and the file table in `README.md`
  name exactly the files in `references/` and `assets/`.
- Every code block names its destination or continues one that did.
- `provenance.md` or the changelog separates fixed, kept and added, and every template oddity has an entry.
- The README follows the section order of section 6 and its footer, author and license lines are the
  standard ones.
- No em-dash, en-dash, arrow, middle dot or smart quote anywhere in the repository's markdown.
- The origin is stated in the words of section 2: no denial, none of the banned words, no corpus figures,
  no defect count or failure story on the front door, and nothing that identifies a system, in the
  frontmatter description included.
- The changelog section, the README version line and the tag agree.
- No file mentions a tool or model as author, and no commit carries an attribution trailer.
